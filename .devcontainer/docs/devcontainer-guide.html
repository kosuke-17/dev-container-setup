Devcontainer Walkthrough — Beginner Guide

.devcontainer の中身を、上から順に読み解く

このリポジトリの .devcontainer/ は、Claude Code を --dangerously-skip-permissions（確認なし実行）で動かすための 使い捨てサンドボックスを定義している。何が起きているかを、devcontainer.json → Dockerfile → firewallスクリプトの順に、 1行ずつ「なぜそう書いてあるか」まで追っていく。

devcontainer.json Dockerfile init-firewall.sh iptables / ipset
Overview

全体像 — なぜコンテナに閉じ込めるのか

Claude Code に「毎回の確認なしでファイル操作・コマンド実行を許可する」と、 誤操作やプロンプトインジェクションでホストPCが壊れるリスクが生まれる。 そこで「ホストのファイルシステムには触れない・外部との通信も絞る」箱を用意し、その中でだけ全権限を渡す。

Host Mac (あなたのPC)
  • generate-deck リポジトリ (~/generate-deck)
  • ~/.claude （認証情報）
  • ~/.ssh, その他すべて
bind mount
→
Container node:20 + Claude Code
  • リポジトリだけを /workspaces にマウント
  • 認証情報は専用volumeのみ
  • node（非root）で実行
egress
firewall
Network 外部通信
  • デフォルト全拒否
  • 許可リストのみ通す
api.github.com
registry.npmjs.org
api.anthropic.com
それ以外の任意サーバ

つまりコンテナは「リポジトリのファイルは自由にいじれるが、それ以外のホスト資産には手が届かず、 外部への通信も許可リストに限定される」箱になっている。以下、この箱を組み立てている3つのファイルを順に見ていく。

01 / Config

devcontainer.json — 箱の「仕様書」

VS Code の Dev Containers 拡張機能が読む設定ファイル。「どのDockerfileでビルドするか」 「何をマウントするか」「起動時に何を実行するか」を宣言する。コード自体は実行されない、純粋な設定。

build.args

Dockerfile に渡す変数。バージョン番号などをここで一元管理し、Dockerfile本体を書き換えずに更新できるようにしている。

runArgs: --cap-add=NET_ADMIN / NET_RAW

Dockerコンテナは初期状態で「ネットワーク設定を変更する権限」を持たない。 後述の firewall スクリプトは iptables でパケットフィルタのルールを書き換えるため、 この2つの capability（Linuxカーネルの権限フラグ）を明示的に追加しないと動かない。

remoteUser: "node"

root ではなく node（非root）ユーザーでシェルに入る設定。 Claude Code は root での --dangerously-skip-permissions 実行を拒否する仕様があるため必須。 rootで確認なし実行ができてしまうと、コンテナ内の被害範囲がroot権限まで広がってしまう。

postStartCommand / waitFor

コンテナ起動のたびに sudo init-firewall.sh を実行し、その完了を待ってから使えるようにする。 firewallの構築に失敗した場合はここでエラーになり、コンテナが「firewallなしで使える」状態にはならない。

mounts — 何を持ち込み、何を持ち込まないか

4つのマウントはそれぞれ役割が違う。特に3・4番目は「壊れたときの被害範囲」を狭めるための設計。

マウント元マウント先目的
claude-deck-bashhistory-*(volume)/commandhistoryシェル履歴をリビルド後も保持
claude-deck-config-*(volume)/home/node/.claudeClaude Codeの認証トークンを保持。ホストの~/.claudeとは別物を新規に作る
~/.claude/CLAUDE.md（read-only bind）/home/node/.claude/CLAUDE.mdグローバル運用ルールだけ共有。読み取り専用なので改変不可
./.devcontainer（read-only bind）.../.devcontainer設定ファイル自身を上書きマウントし、コンテナ内から書き換え不可にする

Why: なぜ ~/.claude を丸ごとマウントしないのか

ホストの ~/.claude には他プロジェクトの認証トークンや設定が入っている。 丸ごと共有すると、コンテナ内の何かが漏洩・悪用した場合にホスト側の認証情報まで巻き添えになる。 代わりに専用のvolumeを新規に作り、コンテナ内で改めてログインする構成にすることで被害を分離している。

Why: なぜ .devcontainer 自体を read-only で上書きマウントするのか

リポジトリ全体は読み書き可能（rw）でマウントされているため、対策がないと コンテナ内から devcontainer.json 自身を書き換えられてしまう。 もし「次回リビルド時にホームディレクトリ全体をマウントする」よう仕込まれると、 リビルドした瞬間にホストの他の場所まで筒抜けになる。設定ファイル自身を読み取り専用で 重ねてマウントすることで、この「未来の自分を騙す」経路を塞いでいる。

02 / Build

Dockerfile — 箱の「中身」を組み立てる

Node.js 20 の公式イメージを土台に、開発に必要なコマンド群とClaude Code CLIを順にインストールしていく。 何をどの順で足しているか、レイヤーごとに見ていく。

apt-get install — なぜこの面子なのか

DockerfileL9–29
# Install basic development tools and iptables/ipset
RUN apt-get update && apt-get install -y --no-install-recommends \
  less git procps sudo fzf zsh man-db unzip gnupg2 gh \
  iptables ipset iproute2 dnsutils aggregate \
  jq ripgrep nano vim \
  && apt-get clean && rm -rf /var/lib/apt/lists/*
日常の開発ツール

git / gh（GitHub CLI）/ jq（JSON整形）/ ripgrep（高速grep）/ vim・nano など、Claude Codeが作業中に叩く基本コマンド群。

iptables / ipset / iproute2 / dnsutils / aggregate — このDockerfileの核心

これらはfirewallを組むための道具そのもの。iptablesでパケットフィルタルールを書き、 ipsetで「許可IPの集合」を高速に管理し、dnsutils（digコマンド）でドメイン名をIPに変換し、 aggregateでIPレンジをまとめる。後述の init-firewall.sh はこれらが無いと1行も動かない。

--no-install-recommends と rm -rf /var/lib/apt/lists/*

推奨パッケージまで芋づる式に入れず、apt自体のキャッシュも消してイメージサイズを抑える定石。動作には影響しない。

git-delta を GitHub Releases から直接落とす

DockerfileL50–54
ARG GIT_DELTA_VERSION=0.18.2
RUN ARCH=$(dpkg --print-architecture) && \
  wget "https://github.com/dandavison/delta/releases/download/${GIT_DELTA_VERSION}/git-delta_${GIT_DELTA_VERSION}_${ARCH}.deb" && \
  dpkg -i "git-delta_${GIT_DELTA_VERSION}_${ARCH}.deb" && \
  rm "git-delta_${GIT_DELTA_VERSION}_${ARCH}.deb"

git-deltaは git diff の出力を見やすく色分けするツール。Debianの標準リポジトリには入っていない（か古い）ため、 aptではなく開発元のGitHub Releasesから .deb パッケージを直接落として dpkg -i でインストールしている。 バージョンを ARG で固定しているのは、ビルドのたびに中身が変わらないようにするため。

非rootユーザーへの切り替えと、npmグローバル領域

USER node の前後

ここまでのapt installやファイル配置はroot権限で行い、以降の作業（npm installやzsh設定）は USER node 以降、非rootユーザーとして行う。最後にfirewallスクリプトの配置だけ 再び USER root に戻り、完了後また USER node に戻す — この行き来がレイヤーごとに明示されている。

NPM_CONFIG_PREFIX=/usr/local/share/npm-global

非rootユーザーのままグローバルnpmパッケージ（後述のClaude Code CLI）を書き込めるように、書き込み先を node ユーザー所有のディレクトリに変更している。

zsh-in-docker と Claude Code CLI のインストール

DockerfileL71–84
# Default powerline10k theme
ARG ZSH_IN_DOCKER_VERSION=1.2.0
RUN sh -c "$(wget -O- https://github.com/deluan/zsh-in-docker/releases/download/v${ZSH_IN_DOCKER_VERSION}/zsh-in-docker.sh)" -- \
  -p git -p fzf -x

# Install Claude
RUN npm install -g @anthropic-ai/claude-code@${CLAUDE_CODE_VERSION}

Note: wget | sh はサプライチェーンの信頼が前提

zsh-in-docker はシェル環境（zsh + powerlevel10k）を1コマンドで整えるインストーラで、 「スクリプトをダウンロードしてそのままシェルに渡して実行する」形式。バージョンは固定しているが、 チェックサム検証まではしていない。ビルド時にネットワーク経由で取得したコードをそのまま実行する、という 性質は理解した上で使う必要がある。

最後の npm install -g @anthropic-ai/claude-code が、このコンテナの主役であるClaude Code CLI本体のインストール。 これでコンテナ内から claude コマンドが使えるようになる。

firewallスクリプトの配置と sudo 権限の限定

DockerfileL86–92
COPY init-firewall.sh /usr/local/bin/
USER root
RUN chmod +x /usr/local/bin/init-firewall.sh && \
  echo "node ALL=(root) NOPASSWD: /usr/local/bin/init-firewall.sh" > /etc/sudoers.d/node-firewall && \
  chmod 0440 /etc/sudoers.d/node-firewall
USER node

node ユーザーに与える sudo 権限を「このfirewallスクリプト1本だけ、パスワード不要で実行可」に限定している。 node ユーザー（＝Claude自身が動かすシェル）が root 権限を持つのはこの一点のみで、他のコマンドをsudoで実行することはできない。

03 / Runtime

init-firewall.sh — 起動のたびに箱を密閉する

コンテナが起動するたび（postStartCommand）に実行され、「まず全部の通信を拒否し、必要な穴だけを一つずつ開けていく」 というデフォルト拒否（default-deny）方式でegress（外向き通信）を制限する。上から順に実行される、実際の手順そのものを追う。

先に：なぜ「許可リスト方式」なのか

「危険なものだけ塞ぐ」ブロックリスト方式だと、想定していない新しい抜け道が常に残り続ける。 反対に「安全と確認できたものだけ通す」許可リスト方式なら、抜け道は原理的に「許可リストに載っているもの」に限定できる。 Claude Codeのようにコンテナ内で任意のコマンドを実行するエージェントを確認なしで動かす以上、後者でないと安心して使えない。

fail-close の罠を仕掛ける（trap ERR）

fail_close() {
    iptables -P INPUT DROP
    iptables -P FORWARD DROP
    iptables -P OUTPUT DROP
    # ip6tablesも同様にDROP
}
trap fail_close ERR

スクリプト全体に set -euo pipefail が効いており、途中でどのコマンドが失敗しても即座に fail_close が発火し、全通信を強制遮断する。「構築の途中で失敗したら、firewallが無いまま 使えてしまう」状態（fail-open）を避けるための保険を、最初に仕掛けておく。

既存ルールを全部フラッシュし、Docker内蔵DNSの経路だけ復元する

iptables -F / -X で以前のルールをまっさらにする。ただしDockerが内部的に使う DNS転送ルール（127.0.0.11宛）は先に退避しておき、フラッシュ後に選択的に戻す。これが無いとコンテナ内の名前解決自体が壊れる。

IPv6を無条件で全遮断する

このスクリプトが制御するのはIPv4（iptables）のみ。IPv6が有効な環境ではIPv4のルールをすり抜けて 素通りしてしまう恐れがあるため、ip6tablesで INPUT / FORWARD / OUTPUT を丸ごとDROPし、 「IPv6は最初から使わせない」ことで対象外にしてしまう。

デフォルトポリシーを DROP に設定する

iptables -P INPUT DROP
iptables -P FORWARD DROP
iptables -P OUTPUT DROP

ここが方式の要。「明示的に許可したルールに一致しない通信は、すべて落とす」という既定値を先に確定させる。 このあとの手順はすべて、この既定のDROPに対して穴を一つずつ空けていく作業になる。

localhostと戻り通信を許可する

lo（ループバック）と、ESTABLISHED/RELATED（すでに成立した通信の戻りパケット）を許可する。 これが無いとコンテナ内のプロセス間通信すら止まってしまう、最低限の穴。

DNSは「実際に設定されているリゾルバ」宛だけ許可する

DNS_SERVERS=$(awk '/^nameserver/ {print $2}' /etc/resolv.conf)
# ↓ /etc/resolv.confから取得した値だけをUDP 53で許可
iptables -A OUTPUT -p udp --dport 53 -d "$dns" -j ACCEPT

名前解決（ドメイン名→IP変換）に使うUDP 53番ポートを、任意の宛先にではなく /etc/resolv.conf に書かれた実際のDNSサーバだけに絞って許可する。 もし任意の外部DNSサーバへの問い合わせを許してしまうと、DNSクエリにデータを埋め込んで外部に送る 「DNSトンネリング」という持ち出し手口の経路になってしまうため。

許可リストを組み立てる間だけ、HTTPS(443)を一時的に全開放する

このあとGitHubのIPレンジをAPI経由で取得する必要があるが、その取得自体がまだ許可リストに 載っていない通信になってしまう「鶏と卵」問題がある。そこで一時的に443番だけ全宛先へ許可し、 許可リストが完成した時点（後述）でこの一時許可を撤回する。

GitHubのIPレンジをまるごと取得して ipset に登録する

gh_ranges=$(curl -s https://api.github.com/meta)
# .web / .api / .git / .pages のCIDRを集約して
echo "$gh_ranges" | jq -r '(.web + .api + .git + .pages)[]' | aggregate -q

GitHubは api.github.com/meta という公開エンドポイントで、自社が使うIPレンジ一覧を公開している。 個別ドメインを1つずつ許可するのではなく、このAPIから正式なIPレンジをまとめて取得し、CIDR形式のまま ipset（IPアドレス集合を高速マッチングできるカーネル機構）に登録する。git clone / push / gh コマンドが 使うIPを漏れなくカバーするための方式。

個別に許可した既知ドメインを名前解決して追加する

for domain in \
    "registry.npmjs.org" "api.anthropic.com" "claude.ai" \
    "console.anthropic.com" "platform.claude.com" "sentry.io" \
    "statsig.anthropic.com" "raw.githubusercontent.com" \
    "marketplace.visualstudio.com" "..."; do
    ips=$(dig +noall +answer A "$domain" | awk '$4 == "A" {print $5}')
    ipset add -exist allowed-domains "$ip"
done

npmパッケージ取得（registry.npmjs.org）、Claude Code自体の通信（api.anthropic.com / claude.ai / console.anthropic.com はOAuthのトークン交換に必須）、 エラー計測（sentry.io）などのために必要な最小限のドメインだけをホワイトリスト化する。 名前解決に失敗したドメイン（例: 廃止されたsub-domain）はスクリプト全体を止めず、警告だけ出してスキップする設計になっている。

一時許可を撤回し、ipset宛の通信だけを最終的に許可する

iptables -D OUTPUT -p tcp --dport 443 -j ACCEPT   # 一時許可を削除
iptables -A OUTPUT -m set --match-set allowed-domains dst -j ACCEPT

先に開けておいた「HTTPS全宛先許可」を削除（-D）し、代わりに ipset allowed-domains に登録された宛先だけを許可するルールに差し替える。ここでようやく 「許可リストに載っているものだけ通る」状態が完成する。

それ以外の全outboundを明示的にREJECTする

iptables -A OUTPUT -j REJECT --reject-with icmp-admin-prohibited

デフォルトポリシーは既にDROP（無言で捨てる）だが、末尾に明示的なREJECTルールを置くことで、 許可されなかった通信に対して「管理者により拒否された」というICMPエラーを即座に返す。 単に無応答でタイムアウトを待たせるより、Claude自身が「この通信は塞がれている」とすぐ判断できる。

最後に、firewallが本当に機能しているか自己検証する

# 許可していないサイトには届かない、という前提を実際にテストする
curl --connect-timeout 5 https://example.com    # → 失敗するのが正解
curl --connect-timeout 5 https://api.github.com/zen  # → 成功するのが正解

許可リストに入れていない example.com には接続できず、許可リストに入っている api.github.com には接続できる — この2つを実際に叩いて確認する。どちらかが期待と逆の結果になったら スクリプトはエラー終了し、postStartCommand が失敗してコンテナ起動が止まる。 「ルールを書いた」ことと「ルールが実際に効いている」ことは別問題なので、必ず動作テストまでを起動シーケンスに含めている。

04 / Rationale

なぜここまでやるのか

この構成が前提にしている、少し意地悪な想定を書いておく。

generate-deck は `input/` に置かれたmdファイルや貼り付けられた文章を取り込んでスライド化するプロダクトで、 Claude Code はユーザーが渡した外部文書をそのまま読む。もしその中に「Claudeへの指示に見せかけたテキスト」 （プロンプトインジェクション）が紛れていた場合、Claudeはそれを実際の指示だと誤認して実行してしまう可能性がある。

--dangerously-skip-permissions はまさにその状態で、ファイル削除やコマンド実行が 逐一の確認なしに走る。だから「悪意ある指示が紛れ込んだ場合でも、被害がコンテナの中とリポジトリのファイルだけに留まり、 ホストPCの他の場所や外部サーバへのデータ持ち出しには広がらない」ことを、設定ファイル側で機械的に保証しておく必要がある。 非rootユーザー・専用の認証情報ボリューム・読み取り専用の設定マウント・デフォルト拒否のegress firewallは、 すべてこの一点のために積み上げられている。

それでも「完全に安全」ではない

リポジトリ自体は読み書き可能でマウントされているため、コンテナ内からファイルやgit履歴を壊すことはできる （バックアップ運用が前提になる）。また許可ドメインの一部は共有CDN上にあり、IPベースの許可だけでは 原理的な限界も残る。「ホストPCの他領域には手が届かない」という一線を守ることに主眼を置いた設計であり、 リポジトリ自体の保護は別途（リモートへのpush等）担保する必要がある。

Glossary

最低限の用語集

devcontainer
VS Codeなどが「このフォルダを開発用コンテナの中で開く」ために読む設定規格。devcontainer.jsonが本体。
bind mount
ホストの特定ディレクトリを、コンテナ内の指定パスにそのまま見せる仕組み。volumeと違い実体はホスト側にある。
named volume
Dockerが管理する独立した保存領域。コンテナを作り直しても中身が消えない。認証情報の永続化に使われる。
egress
コンテナ・サーバから外部への「出て行く」通信のこと。対義語はingress（入ってくる通信）。
iptables
Linuxカーネルのパケットフィルタを操作するコマンド。「この条件に一致する通信をACCEPT/DROP/REJECTする」というルールを積み上げる。
ipset
大量のIPアドレス／CIDRを1つの集合として登録し、iptablesから高速に参照できるようにする仕組み。
CIDR
192.30.252.0/22のような表記で、単一IPではなく「範囲」を表す。GitHubのIPレンジなどはこの形式で公開される。
fail-close / fail-open
処理が失敗したとき、安全側（全遮断）に倒れるのがfail-close、逆に無防備側（全通過）に倒れるのがfail-open。firewallはfail-closeであるべき。
capability (NET_ADMIN等)
rootの権限を細かく分割したLinuxカーネルのフラグ。コンテナは既定でほとんどのcapabilityを持たない。
